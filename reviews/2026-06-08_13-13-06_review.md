## 🚨 1. Security & Vulnerabilities

*Focus: Hardcoded secrets, injection risks (SQL, XSS, Command), path traversal, insecure dependencies, authorization bypass.*

**Issues Found:**

* **[HIGH] `appsettings.json` contains `DP_PASSPHRASE` key with an empty value** (`appsettings.json:32`). If the key is left empty and the app starts, data-protection keys are written to disk **unencrypted**. There is no startup-time validation that warns the operator. A misconfigured production deployment silently has no encryption-at-rest.

* **[HIGH] `CultureController.Set` is completely unauthenticated** (`CultureController.cs:9`). Any unauthenticated caller can hit `/Culture/Set?culture=<value>&redirectUri=<local>` and set an arbitrary culture cookie. The controller also lacks an `[HttpPost]` attribute, so the culture change is triggered via a `GET` request, making it potentially vulnerable to CSRF even with `SameSite=Lax` in some cross-site scenarios. Recommend adding `[Authorize]` and switching to `[HttpPost]` + antiforgery.

* **[MEDIUM] `MatrixAuthenticationStateProvider` stores the raw Matrix `AccessToken` in a `ClaimsPrincipal` claim** (`MatrixAuthenticationStateProvider.cs:55`) and also in `ProtectedLocalStorage` (`MatrixAuthenticationStateProvider.cs:91-92`). While the cookie is `HttpOnly` and `Secure`, the token is replicated to browser-side storage. If XSS was ever introduced, both stores would be compromised simultaneously. Consider storing only a server-side session reference in browser storage instead of the raw access token.

* **[MEDIUM] `ProtectMediaAsync` in `SynapseAdminGateway.cs` uses only `mediaId` in the URL, dropping `serverName`** (`SynapseAdminGateway.cs:365`):
  ```csharp
  var url = $"/_synapse/admin/v1/media/protect/{mediaId.UrlEncode()}";
  ```
  The Synapse API path for this endpoint includes the server name. `UnprotectMediaAsync` has the same issue (`SynapseAdminGateway.cs:372`). This means protect/unprotect may silently succeed against the wrong URL or return 404s for remote media.

* **[LOW] `AuthController.SignOutAction` has no `[Authorize]` attribute** (`AuthController.cs:54`). An unauthenticated user can call `/Auth/SignOutAction` unnecessarily. Low risk but not defensive.

* **[LOW] `CultureController` sets the culture cookie without `HttpOnly = true`** (`CultureController.cs:17-20`). The culture cookie itself is not sensitive, but for defence-in-depth it should be `HttpOnly`.

**Recommended Fixes:**

* Add a startup guard in `Program.cs` to log a `LogWarning` if `DP_PASSPHRASE` is empty in Production:
  ```csharp
  if (string.IsNullOrEmpty(passphrase) && !builder.Environment.IsDevelopment())
      Log.Warning("DP_PASSPHRASE is not configured. Data Protection keys will NOT be encrypted at rest.");
  ```
* Add `[Authorize]` and `[HttpPost]` to `CultureController.Set`. Use a form POST + antiforgery token from the language selector component.
* Decorate `AuthController.SignOutAction` with `[Authorize]`.
* Verify and fix the `ProtectMediaAsync`/`UnprotectMediaAsync` URL construction in `SynapseAdminGateway.cs` against the Synapse API docs.

## 🐛 2. Bugs & Logic Errors

*Focus: Edge cases, Null-Reference risks, race conditions, off-by-one errors, infinite loops, incorrect async/await usage.*

**Issues Found:**

* **[HIGH] `RoomDetails.razor.cs` polling loop swallows all exceptions silently** (`RoomDetails.razor.cs:351-354`):
  ```csharp
  catch (Exception)
  {
      // Ignore to prevent circuit crash
  }
  ```
  If `GetPurgeHistoryStatusAsync` fails repeatedly (e.g., network error), the loop silently retries every 5 seconds indefinitely with no timeout and no way for the user to know something has gone wrong. This is an infinite-retry anti-pattern. Add a maximum retry count or a timeout on `_pollingCts`.

* **[MEDIUM] `PurgeHistoryDialog.razor.cs` calls `PurgeRoomHistoryAsync` without a `CancellationToken`** (`PurgeHistoryDialog.razor.cs:80`):
  ```csharp
  var result = await RoomService.PurgeRoomHistoryAsync(RoomId, request);
  ```
  This means closing the dialog or navigating away does not cancel the in-flight purge request. The overload with no token defaults to `default`, which is an uncancellable token.

* **[MEDIUM] `UserDetails.razor.cs` constructs `mxc://` URIs from `media.MediaId`** (`UserDetails.razor.cs:89, 110, 131, 152`) by prepending `mxc://{ServerName}/`. If `UserMediaItemViewModel.MediaId` from the Synapse API is already a full `mxc://` URI (rather than just the ID part), the constructed URI would be malformed. This needs explicit validation or documentation.

* **[MEDIUM] `MatrixSessionService.LoginAsync` does not catch `OperationCanceledException` separately** (`MatrixSessionService.cs:29-33`). All login failures return the same generic `L["LoginFailed"]` message, making it impossible for the user to distinguish a network timeout from bad credentials.

* **[LOW] `Home.razor.cs` imports `SynapseAdmin.Infrastructure.Gateways`** (`Home.razor.cs:5`). This is a layer-boundary violation — the Presentation layer should not reference the Infrastructure namespace directly. Verify this `using` is not used and remove it; it may be a leftover from when type-checks like `is SynapseAdminGateway` existed before the `SupportsAdminApi` property was introduced.

* **[LOW] `RoomService._activePurges` dictionary is `Scoped`**, meaning purge-tracking state is per-circuit only. State is lost when the user navigates away and back in a new circuit. This is consistent with the current behavior (purge ID is stored and read from the same scoped service instance), but it is surprising and should be documented.

**Recommended Fixes:**

* Add a max-retry limit and error Snackbar to the polling loop in `RoomDetails.razor.cs`.
* Pass a `CancellationToken` from a dialog-owned `CancellationTokenSource` to `PurgeRoomHistoryAsync`.
* Add XML doc comment or validation to `UserMediaItemViewModel.MediaId` to document whether it is the raw media ID or a full `mxc://` URI.
* Add a separate `catch (OperationCanceledException)` in `MatrixSessionService.LoginAsync`.
* Remove the unused `using SynapseAdmin.Infrastructure.Gateways;` from `Home.razor.cs`.

## ⚡ 3. Performance & Efficiency

*Focus: Inefficient algorithms (Big-O), memory leaks, unnecessary API calls, synchronous blocking in async code, excessive rendering in Blazor.*

**Observations:**

* **[MEDIUM] `RoomService.GetMediaMetadataBatchAsync` fires N concurrent HTTP requests with no concurrency limit** (`RoomService.cs:141-168`). For a room with hundreds of media items, this spawns hundreds of simultaneous `HttpClient` requests. This can saturate the connection pool and cause timeouts.

* **[MEDIUM] `MediaController` calls `RestoreSessionAsync` on every single media request** (`MediaController.cs:42, 84`). While the short-circuit guard in `RestoreSessionAsync` prevents re-authentication when the token matches, this still executes the comparison logic and property access on every download. If the short-circuit is effective, the cost is low; if not (e.g., different Scoped service instance), it issues full homeserver discovery calls per request. This should be profiled.

* **[MEDIUM] `ThemeService.DiscoverThemes()` uses reflection** (`ThemeService.cs:107-141`). Since `ThemeService` is `Scoped`, discovery runs once per circuit. For a large number of connections this is repeated reflection. Registering as `Singleton` (if no per-circuit state is needed beyond `localStorage` calls) with a cached discovery result would be more efficient.

* **[LOW] `SynapseAdminGateway.GetSynapseCompatibilityJsonOptions()` creates a new `JsonSerializerOptions` on every call** (`SynapseAdminGateway.cs:28-31`). The comment explains the workaround (LibMatrix mutates options). This causes GC pressure. Consider cloning from a frozen template instance rather than constructing fresh each time.

* **[LOW] `UserDetails.razor.cs` calls `LoadUserDetails()` (full reload including memberships and all media) after each single media operation** (`UserDetails.razor.cs:102, 123, 144, 163`). A targeted `ReloadMedia()` method would avoid the unnecessary membership/state re-fetch.

**Optimization Suggestions:**

* Add `SemaphoreSlim(10, 10)` in `GetMediaMetadataBatchAsync` to cap parallel media metadata fetches.
* Consider registering `ThemeService` as `Singleton` with lazy-initialized theme discovery.
* Add a comment in `MediaController` confirming the `RestoreSessionAsync` short-circuit behavior is the expected performance path.
* Extract a `ReloadMedia()` method in `UserDetails.razor.cs` that only refreshes media data.
