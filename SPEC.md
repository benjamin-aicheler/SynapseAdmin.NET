## 1. Summary

SynapseAdmin.NET is a self-hosted .NET 10 Blazor Server web application for administering Matrix Synapse (>= 1.145.0) and Synapse-Admin-API-compatible homeservers (such as Tuwunel >= 1.8.2). It gives homeserver administrators a modern, localized, browser-based console for managing users, rooms, media, moderation reports, event forensics, registration tokens, federation queues, server notices, and database background updates without requiring direct CLI or database access.

## 2. Background & Problem

Managing a Matrix Synapse (or compatible) homeserver natively relies on raw HTTP Admin API requests, command-line scripts, or direct database inspection—workflows that are slow, error-prone, and difficult to use safely for routine moderation and media auditing. Additionally, exposing raw homeserver admin endpoints directly to browser SPAs can introduce CORS, credential-exposure, or reverse-proxy complexity, while newer compatible homeservers (such as Tuwunel >= 1.8.2) require tolerant API handling beyond Synapse-only SDK assumptions.

SynapseAdmin.NET addresses this by acting as a dedicated, containerized administration server that proxies Matrix and Synapse Admin requests server-side, encrypts session material at rest, enforces strict SSRF and cookie security policies, and presents high-density Material Design workflows via MudBlazor.

## 3. Goals

- Deliver complete browser-based homeserver administration across users, rooms, room directory, media moderation/cleanup, event reports, raw event forensics, registration tokens, federation destinations, server notices, and background database jobs.
- Support both Synapse (>= 1.145.0) and compatible homeservers (e.g., Tuwunel >= 1.8.2), while gracefully detecting non-admin Matrix servers and informing the user when admin APIs are unavailable. Synapse's documented behavior is the contract for every homeserver: the UI describes each operation as Synapse documents it, and on another server an operation whose result can't match Synapse's fails with a "not supported" message instead of behaving differently. A difference the gateway can't correct is accepted only if the operation does what Synapse does and only a read's matching or listing differs, or what the server does later on its own; each accepted difference is recorded in §10.
- Protect administrator credentials, target homeservers, and internal networks via SSRF-checked discovery (`HOMESERVER_ALLOWLIST`), AES-256-GCM encrypted Data Protection keys (`DP_PASSPHRASE`), `Secure` HTTP-only cookies, browser-bound session handoff, and login rate limiting.
- Provide responsive, secure media inspection (streaming previews, downloads, HTTP byte-range seeking, quarantine/protection controls) without buffering large files on the server.
- Support internationalized administration (`en-US`, `de-DE`, `fr-FR`), browser-local timezone interpretation, and customizable UI themes.

### Non-Goals (explicitly out of scope)

- **General Matrix end-user client functionality:** End-user messaging, room participation, or E2EE key management for non-admin Matrix users are out of scope.
- **Direct homeserver database access:** All operations communicate exclusively through Matrix Client-Server, Federation version, and Synapse Admin HTTP APIs.
- **Local user database or separate RBAC system:** SynapseAdmin.NET stores no local accounts or permissions; authentication and admin authorization are enforced by the target homeserver.
- **Homeservers without the Synapse Admin API:** SynapseAdmin.NET supports only Synapse and Synapse-compatible homeservers ([ARCHITECTURE.md](./ARCHITECTURE.md) §11). It offers no features of other admin APIs, such as another server's own admin endpoints or admin room commands. On a homeserver without the Synapse Admin API, the admin can still sign in and use the Client-Server features, such as the public room directory and aliases. Every admin operation there is refused as "not supported by this homeserver".
- **Third-party and SSO identity management:** SynapseAdmin.NET doesn't show or change a user's third-party IDs (`threepids`, such as email addresses and phone numbers) or external SSO IDs (`external_ids`), which the Synapse Admin API's user endpoints accept (#584).
- **Fixed multi-tenant SLAs or offline/air-gapped bundling:** No uptime/concurrency SLAs are mandated, and external font CDN loading (`fonts.googleapis.com`) is accepted for now without offline asset bundling.

## 4. Users & Use Cases

| User / role | Need | Use case |
|---|---|---|
| Homeserver Administrator | Authenticate safely without exposing tokens in URLs or risking SSRF | Log in with Matrix username/password or access token against an allowlisted or public HTTPS homeserver |
| Homeserver Administrator | Monitor server health and resource hotspots at a glance | View server brand/version, user/room/report totals, latest users/reports, largest rooms, and top media uploaders on the dashboard |
| Homeserver Administrator | Manage user lifecycle, permissions, and uploaded media | Search, create, deactivate/erase, renew validity, shadow-login, toggle experimental features, and audit/quarantine/delete user media |
| Homeserver Administrator | Moderate rooms, messages, and media | Inspect room metadata/state/members/messages, purge history, block/delete rooms, manage public directory visibility/aliases, and browse media galleries |
| Homeserver Administrator | Regain control of a room whose admins are unavailable (#587) | Make themselves or another user room admin through a local member who still holds the power, or join a local user to the room |
| Homeserver Administrator | Investigate abuse and regulate server growth | Review/dismiss event reports, inspect raw unredacted events by ID, send server notices, and manage registration tokens |
| Homeserver Administrator | Maintain federation and server storage/DB health | Inspect failing federation destinations and reset retry timeouts; pause/resume/trigger DB background updates; purge remote media cache and old local media |

### User Stories

- As a **Homeserver Administrator**, I want to log in using either username/password or an access token so that I can administer my homeserver regardless of how my admin account is provisioned.
- As a **Homeserver Administrator**, I want to inspect and stream user or room media (including video/audio seeking) and quarantine, protect, or delete specific files so that I can moderate content safely without leaking quarantined objects.
- As a **Homeserver Administrator**, I want to inspect unredacted raw event JSON and purge room history up to a message or timestamp in my local timezone so that I can investigate and remediate moderation incidents accurately.
- As a **Homeserver Administrator**, I want destructive actions on detail pages to validate that the displayed entity matches the confirmed target so that rapid navigation never affects the wrong user or room.

## 6. Non-Functional Requirements

| ID | Category | Requirement |
|---|---|---|
| NFR-1 | Performance | Media streams must be relayed from upstream response headers without full-file server buffering (`ResponseOwningStream`), honoring upstream `Range` requests. Large tables (`/users`, `/rooms`, `/reports`, user media) must use server-side pagination (`/federation` loads its destinations once and pages locally, FR-11), and route changes must cancel superseded in-flight requests. |
| NFR-2 | Security / privacy | Authentication cookies must set `HttpOnly`, `SameSite=Lax`, and `CookieSecurePolicy.Always`. Data Protection keys on disk must be encrypted with AES-256-GCM when `DP_PASSPHRASE` is set. Untrusted strings must be sanitized before logging (`.SanitizeForLogging()`), and technical exception details must never be shown to users. Container runs as non-root `app` (`UID 1654`). |
| NFR-3 | Availability | Application restarts must preserve valid user sessions when `./keys` and `DP_PASSPHRASE` are persisted. Multi-replica deployments must support sticky sessions and shared `/app/keys`. Non-admin homeservers must degrade gracefully with localized capability alerts rather than crashing. |
| NFR-4 | Accessibility | UI must use MudBlazor Material Design components, semantic headings with focus management (`FocusOnNavigate`), RTL support (`MudRTLProvider`), and responsive breakpoints across desktop and mobile viewports. |
| NFR-5 | Compatibility | Targets .NET 10 (`net10.0`), modern desktop/mobile browsers with WebSockets and ES modules, `linux/amd64` and `linux/arm64` Docker images, Matrix Synapse >= 1.145.0, and Tuwunel >= 1.8.2 (including JSON/timestamp/field-naming compatibility workarounds; operations whose result can't match Synapse's are refused, AC-14). |

## 7. Acceptance Criteria

- **AC-1 (FR-1, Auth Bridge):** Given an authenticated login in a Blazor circuit, when `AuthCookieService.EstablishCookieSessionAsync` creates a bridge key, then `SessionBridgeService` binds it to the circuit's antiforgery token, `POST /Auth/SignIn` redeems it atomically at most once within 60 seconds via request body (never URL query), and issues `.AspNetCore.Cookies` (`AuthCookieServiceTests`).
- **AC-2 (FR-2, SSRF Policy):** Given an empty `HOMESERVER_ALLOWLIST`, when a user enters a public `https://` homeserver, discovery proceeds; when a user enters or a `.well-known`/redirect/DNS resolution targets `http://` or an internal/private/loopback/link-local IP, discovery fails with `HomeserverNotAllowedException` and shows a localized error without leaking technical details (`HomeserverDestinationPolicyTests`).
- **AC-3 (FR-2, Rate Limiting):** Given 5 failed password login attempts within 1 minute for the same IP or `(homeserver, username)`, when a 6th attempt occurs, then `LoginRateLimiter` blocks the attempt and returns `TooManyLoginAttempts`; token logins throttle per IP only (`SecurityInfrastructureTests`).
- **AC-4 (FR-4, User Media Pagination & Totals):** Given a user with uploaded media, when the User Details Media tab loads, then it requests page `from = page * pageSize` ordered `created_ts`/`b`, queries overall totals via localpart search on `/_synapse/admin/v1/statistics/users/media`, and labels page statistics separately from overall totals (`UserMediaPaginationTests`, `UserDetailsMediaTabTests`).
- **AC-5 (FR-5, FR-4, Stale-Selection Guard):** Given `RoomDetails` or `UserDetails` navigating from entity A to entity B, when A's request finishes late or B's load fails, then A's data and action buttons are never displayed and destructive confirmations target only the currently displayed entity ID (`RoomDetailsStaleSelectionTests`, `UserDetailsStaleSelectionTests`). Given the room gallery page (`/rooms/{RoomId}/gallery`, FR-6) switching from room A to room B while A is still loading, A's load is cancelled, A's late answer shows no name, media, alert or snackbar, and the page keeps loading until B's answer arrives (`RoomGalleryStaleSelectionTests`, #495). A late purge status answer or polling failure for room A, or for an older purge in the same room, changes neither the shown purge, the tracked purge in the shared cache, nor the notifications (`RoomDetailsStaleSelectionTests`, #522). Given the event forensics page (`/forensics?eventId=…`, FR-9) switching from event A to event B while A is loading, B is requested at once and A's late answer shows no details or snackbar; removing the query clears the shown event, while an event ID typed on `/forensics` stays (`EventForensicsStaleSelectionTests`, #521).
- **AC-6 (FR-6, Media Deduplication):** Given a room whose `/_synapse/admin/v1/room/{roomId}/media` response contains duplicate `mxc://` URIs, when rendered in `RoomDetails` or `RoomGalleryGrid`, then each unique `mxc://` URI (compared ordinally) appears once preserving first-seen order (`RoomMediaDeduplicationTests`, `RoomGalleryDuplicateMediaTests`).
- **AC-7 (FR-8, Conditional & Ranged Media):** Given a request to `/Media/Download`, `/Media/Preview`, or `/Media/Avatar`, when `If-None-Match` matches (including `*`), the controller validates authorization and upstream media existence before returning `304 Not Modified` (returning `404` if missing/quarantined); when a valid single `bytes` `Range` is supplied, it forwards the range upstream and relays `206 Partial Content` with `Content-Range` (`MediaControllerConditionalTests`, `MediaRangeForwardingTests`).
- **AC-8 (FR-14, Timezone & DST):** Given an IANA browser timezone, `TimeZoneService` converts timestamps to local time, advances invalid DST spring-forward times by 1 hour, and resolves ambiguous DST fall-back times to the earlier occurrence (`TimeZoneAndPurgeTimestampTests`). Editing a registration token without changing its expiry keeps the stored instant, also when it is the second occurrence of an ambiguous time (#520).
- **AC-9 (NFR-5, Synapse Quirks):** Given numeric `next_token` values, millisecond `creation_ts` on v3 user lists vs second `creation_ts` on v2 user details, and `avatar` keys on room admin responses, deserialization and mapping complete without errors (`JsonStringConverterTests`, `MappingExtensionsTests`).
- **AC-10 (FR-6, Gallery Filters Before Metadata, #523):** Given a room gallery with 21 items of which only item 21 is an image with the searched file name, and the metadata of the first 20 already loaded, when the admin selects Images or searches for that file name, then the gallery looks up item 21 and shows it. Without a search or type filter, the gallery still looks up metadata only for the items it displays (20 per page). One load looks up at most 5 batches of 20 items; if matches are still missing and items are left unchecked, the gallery shows "Checked x of y items" with a "Check more" button instead of "All loaded" or "No media found". A filter change during a lookup discards the older filter's results. Items whose type stays unknown after the lookup (for example uncached remote media) are not shown under any type filter, including Files, and the gallery says how many it hides (`RoomGalleryFilterHydrationTests`).
- **AC-11 (FR-5, Room Deletion Status, #518):** Given an admin who confirms Delete or Delete & Block, when the homeserver answers with a `delete_id`, then the page shows "room deletion requested", stays on the room page, shows the deletion banner and checks `/_synapse/admin/v2/rooms/delete_status/{delete_id}` every 5 seconds. `scheduled` and `active` keep the banner. `complete` reports the deletion and shows the room as deleted. `failed` reports a localized failure, and Synapse's error text goes only to the log. An unknown deletion (`404`) and 5 failed status requests in a row each remove the banner and report it. An answer without `delete_id` shows "room deletion requested" without a banner. Opening a room with a scheduled or running deletion (`/_synapse/admin/v2/rooms/{roomId}/delete_status`) shows the banner and checks the status. A homeserver without that endpoint shows no banner and no error. A late status answer for a room that is no longer shown, or for an older deletion, changes nothing. While the deletion banner or the purge banner is shown, all room actions are disabled. A failed purge shows the localized "history purge failed" message without the homeserver's error text, which goes only to the log. On Tuwunel, Delete and Delete & Block are refused after confirmation with the "not supported by this homeserver" warning, nothing is sent and no banner appears, and opening a room sends no status request and shows no banner and no error (#559) (`RoomDetailsRoomDeletionTests`, `RoomDetailsStaleSelectionTests`, `RoomServiceCharacterizationTests`, `SynapseAdminGatewayCharacterizationTests`).
- **AC-12 (FR-4, Shadow Login Expiry, #539):** Given an admin who clicks "Login as User (Shadow)" on a user's page, when the homeserver issues the token, then the request is `POST /_synapse/admin/v1/users/{userId}/login` with the expiry one hour from now as the integer `valid_until_ms` (Unix milliseconds) in the JSON body and no query string, and the message says how many minutes the token is valid (`SynapseAdminGatewayCharacterizationTests`, `UserServiceCharacterizationTests`).
- **AC-13 (FR-5, Room List Sorting, #540, #541, #545):** Given the room list (`/rooms`), then only Name, Creator, Members and Public are sortable, and Room ID and Room Type are plain headers, because the admin API sorts by neither. The dashboard counts rooms with `order_by=name`, and no request sends the deprecated `alphabetical`. When the admin sorts Members ascending, the smallest rooms come first on Synapse (`dir=b`, since Synapse sorts member counts largest first) and on Tuwunel (`dir=f`, since Tuwunel sorts ascending); descending puts the largest first on both. Name, Creator and Public send `dir=f` ascending and `dir=b` descending on both (`RoomListSortingTests`, `SortDirectionMappingTests`, `SynapseAdminGatewayCharacterizationTests`, `MatrixAuthGatewayProbeTests`).
- **AC-14 (NFR-5, Unsupported Operations):** Given a homeserver whose gateway can't match Synapse's result for an operation, when the admin starts that operation, then no request for it reaches the homeserver, the result is a failure with the localized "not supported by this homeserver" message in EN, DE and FR, and the page shows the same labels, options and confirmation as on Synapse. The result is a warning, not an error (`GatewayCallExtensionsTests`, `GenericMatrixGatewayTests`, `MediaServiceCharacterizationTests`).
- **AC-15 (FR-8, Bulk Local Media Deletion, #542):** Given the Delete Local Media card on `/media-maintenance`, then the age field is labeled "Last accessed before (days)", and the description says that media last accessed before the cutoff (or uploaded then, if never accessed) and larger than the size is deleted, that both conditions must apply, and that protected and quarantined media are kept, in EN, DE and FR. When the admin deletes, the confirmation names the days and the size ("whatever their size" for 0 MB) and says whether media used as a profile picture or room avatar is kept or deleted, following the switch. After the deletion, the message names the number of deleted files the homeserver reports (`total`), also when it is 0, and never shows a raw placeholder. On Tuwunel, the request is refused after confirmation with the "not supported by this homeserver" warning, and nothing is sent (`MediaMaintenanceTests`, `MediaServiceCharacterizationTests`, `SynapseAdminGatewayCharacterizationTests`).
- **AC-16 (FR-11, Federation Destination Paging, #551):** Given the federation page (`/federation`), when it loads, then the first request sends no `from`, each later request sends the previous `next_token` unchanged (URL-encoded), and loading stops only when a response has no `next_token`, whatever `total` says. If a request fails or the homeserver repeats a `next_token`, the page shows the localized error and no destinations, and the next reload loads again. Searching, sorting and paging a complete load send no request (`FederationServiceCharacterizationTests`, `FederationDestinationsLoadTests`, `SynapseAdminGatewayCharacterizationTests`).
- **AC-17 (NFR-5, Tuwunel Admin API Coverage):** Given a Tuwunel server, when the login probe reports a version below 1.8.2, then the session gets no admin API, as on a generic Matrix server; 1.8.2 and later, and a version that can't be parsed, get the Tuwunel gateway. When the admin starts an operation that Tuwunel doesn't serve (quarantine and unquarantine of media, a room's or a user's media, protect and unprotect, shadow-banning a user and lifting it, event reports, a report's details and deleting one, account validity, experimental features, background updates, the largest rooms by database size) or that it runs with different semantics (the remote media cache purge, a user list sorted by anything but user ID), then no request for it reaches the homeserver and the page shows the "not supported by this homeserver" warning. A read that a page runs by itself when it opens logs the refusal at `Debug` instead of as an error. The dashboard (latest reports, latest users, largest rooms) and user details (experimental features) show no snackbar for it, while the event report and background update pages show the warning. The dashboard still shows the total user count. A creation date that Tuwunel doesn't store (`creation_ts` `0` or missing) is shown as "unknown" in the user list, on user details and on the dashboard, in EN, DE and FR, instead of a 1970 date (`SynapseAdminGatewayCharacterizationTests`, `MatrixAuthGatewayProbeTests`, `GatewayCallExtensionsTests`, `MappingExtensionsTests`, the service characterization tests, and bUnit tests of the dashboard and the user pages).

## 10. Edge Cases & Error Handling

- **Silent cancellation:** `OperationCanceledException` returns `OperationResult.Cancelled()` (`Severity.Normal`), suppressing error snackbars in Blazor components during navigation or rapid reloads.
- **Safe error messaging:** Exception messages, stack traces, and `HomeserverNotAllowedException` technical reasons are logged server-side only; users receive localized friendly messages from `SharedResources`.
- **Plain HTTP cookie rejection:** Non-localhost HTTP access cannot store `CookieSecurePolicy.Always` cookies; `NavMenu` warns the user (`HttpsRequiredForMediaWarning`) and skips cookie sync, while `AuthController.SignIn` logs a warning.
- **Missing client IP:** If a reverse proxy omits client IP (e.g., Unix socket) or is not in `TRUSTED_PROXIES`, `ClientIdentityCircuitHandler` and `MatrixSessionService` log a warning and fall back to the shared `"unknown"` rate-limit bucket rather than per-circuit random keys.
- **Missing room on the gallery page:** If `/rooms/{RoomId}/gallery` can't load the room, the page shows the error once as a snackbar and in an alert ("room not found" if the result has no message), with a button back to the room list. It doesn't render an empty gallery, which would load the room a second time (#480). If the room loads but the homeserver returns no media list (`null`), the room has no media: the gallery shows "No media found" without loading the room again, and the room's media tab shows empty tables instead of a spinner (#524).
- **Gallery filters and unknown metadata (#523):** Room media arrives as bare `mxc://` URIs, and Synapse has no bulk metadata endpoint, so each metadata lookup is one admin API request (10 in parallel). A type filter or a file-name search therefore checks the room's items in order, 100 lookups per load at most, and asks the admin before checking more. An item whose lookup returns no type (uncached remote media returns `404`) counts as "type unknown": it isn't retried, it only appears under the All type filter, and the type filters report how many items they hide for this reason. A search still matches an item by its `mxc://` URI without a lookup.
- **Homeservers without authenticated media:** Media is fetched from the authenticated `/_matrix/client/v1/media/download` endpoint first. If the homeserver doesn't support it (`M_UNRECOGNIZED`, or a bare `404`/`405`), the legacy `/_matrix/media/v3/download` endpoint is used instead. Media the homeserver reports as missing (`M_NOT_FOUND`) isn't requested again from the legacy endpoint.
- **Synapse/Tuwunel inconsistencies:** Lists load when `next_token` is a number instead of a string. User creation dates are correct on the user list (milliseconds) and on user details (seconds). Room avatars (`avatar` in the room admin API) and user avatars (`avatar_url`) both display. The dashboard's largest rooms show names although `/statistics/database/rooms` returns none. A user's overall media totals are found by a localpart search on `/statistics/users/media`. Each `mxc://` URI appears once per room (AC-6, AC-9).
- **Room deletion status (#518):** Synapse's Admin API docs say that it keeps a deletion's status for 24 hours after the deletion finishes, or until Synapse restarts; Synapse v1.165.0's task scheduler keeps finished tasks in its database for 7 days. Once the status is gone, reopening the room shows no banner, and a status that disappears while the page checks it is reported as "status unknown". A homeserver that returns no `delete_id`, or that has no status endpoints, gets only the "requested" message. A deletion still running in another session can make a new deletion request fail, which shows the usual "error deleting room" message.
- **Shadow login tokens issued by v1.16.1 or earlier (#539):** These versions sent the expiry as a query parameter, which Synapse ignores, so those tokens never expire. The fix doesn't end them: an admin who handed out such a token ends it with the standard `/logout` call made with that token. Tuwunel 1.8.2 and later serve this endpoint as Synapse does, reading the expiry as `valid_until_ms` from the JSON body, so the app doesn't refuse it on Tuwunel (#558). Tuwunel 1.8.1, which doesn't serve it, is no longer supported (see "Tuwunel versions").
- **Room list sort direction by server (#541):** Synapse sorts `joined_members`, `joined_local_members`, `version`, `state_events` and `size` largest first; Tuwunel (1.8.1 to 2.0.0) sorts every key ascending. The app follows the Synapse docs and reverses `dir` for these keys only on Tuwunel. A homeserver whose brand couldn't be resolved, but which serves the admin API, is treated like Synapse. Ties sort by room ID in the same direction on both.
- **Room list filters by server (#588):** Synapse v1.165.0 filters `public_rooms` by directory visibility (`rooms.is_public`) and `empty_rooms` by `joined_members = 0`, and counts `total` with the same filter. Tuwunel (1.8.2, 2.0.0) filters by directory visibility too, but `empty_rooms` by `joined_local_members == 0`, also before counting and paging. Both select the same rooms: when Synapse's last local user leaves a room, it deletes the room's current state and counts every member as having left, so `joined_members` drops to `0`; while a local user is joined, the room isn't empty on either server. Synapse updates these counts in the background, so a room that was just emptied can take a moment to appear under "Only empty".
- **Event report details and filters (#588):** In Synapse v1.165.0 (and 1.145.0) the list matches `room_id` and the reporter's `user_id` as substrings and `event_sender_user_id` exactly, combines them with AND, and counts `total` with the same filter, although the reference says `total` reflects only `user_id` and `room_id`. A reported event that was purged has no sender and never matches the reported-user filter. The details read joins the event's stored JSON and the room's state, so it answers `404` for a report whose event was purged or whose room was deleted, while the list still shows it. The stored JSON can hold a redacted event's original content until Synapse prunes it (`redaction_retention_period`, 7 days by default), so the dialog may show content that room members no longer see.
- **Event context (#588):** Synapse v1.165.0 splits `limit` into `floor(limit / 2)` events before and the rest after, returns `events_before` newest first, and answers `404` when the event isn't in the given room, so the page always passes the room the event names. The admin API skips the visibility checks, but redacted events come back pruned, as clients see them; the forensics view of each event (`fetch_event`) shows the stored original. Tuwunel 1.8.2 and 2.0.0 split `limit` the same way, cap it at 100, order `events_before` the same and answer `404` for an event in another room; for a room it doesn't know they answer `403`, which the page shows as an error. When an event isn't stored locally, Tuwunel may fetch it over federation if its configuration allows, which Synapse never does; the page only asks for events it has already fetched.
- **Operation not supported by the homeserver:** An operation that the homeserver's gateway can't carry out with Synapse's result fails with a localized "not supported by this homeserver" message and changes nothing on the server. The page doesn't hide or reword the operation for that server. The same message replaces the operation's own error message on homeservers without the admin API, whose gateway already refuses admin operations.
- **Registration tokens on Tuwunel (#548):** Tuwunel (1.8.1 to 2.0.0) deletes a registration token as soon as it is invalid (its uses reached the cap, or its expiry passed), the next time tokens are listed or checked. Synapse keeps such a token and lists it as invalid. The app refuses, with the "not supported by this homeserver" warning, a create or update that would leave the token invalid at once: max uses `0`, max uses at or below its uses so far, or an expiry in the past. The dialog looks the same as on Synapse. A token that runs out or expires later still disappears from `/tokens` on Tuwunel; the app can't prevent that.
- **Room deletion on Tuwunel (#559):** Tuwunel 1.8.1 and 2.0.0 serve `DELETE /_synapse/admin/v2/rooms/{roomId}` and both status endpoints with Synapse's status names, but their deletion doesn't keep Synapse's guarantee. Synapse doesn't purge a room while local users are still joined; Tuwunel records the users it couldn't evict and purges anyway, and logs some failed purge steps (such as deleting the events) without reporting them. Its `complete` can therefore report a deletion that Synapse would have reported as failed. Its status also has no `error` text, leaves scheduled deletions out of a room's list, and is kept only in memory (lost on restart, removed after 7 days). The app refuses the deletion and both status reads on Tuwunel with the "not supported by this homeserver" warning and sends nothing. The room page shows no deletion banner there, also for a deletion started in another tool, and Delete and Delete & Block look the same as on Synapse.
- **Tuwunel versions:** Tuwunel 1.8.1 doesn't serve seven endpoints the app calls (media metadata, a room's media list, the remote media cache purge, user media statistics, federation destinations, server notices and shadow login); 1.8.2 serves all of them. The app therefore requires Tuwunel >= 1.8.2 for the admin pages. A 1.8.1 server is treated like a Matrix server without the admin API: the admin can sign in, and the app says that the admin API isn't available.
- **Synapse versions (#612):** Checked against Synapse's source (the first release tag that serves each endpoint or parameter the gateways send). The app requires Synapse >= 1.145.0 for the admin pages; an older Synapse is treated like a Matrix server without the admin API (AC-29). The newest requirements: `GET /_synapse/admin/v1/users/{userId}/memberships` (1.145.0, the user page's rooms and the join dialog's picks), `GET /_synapse/admin/v1/media/{serverName}/{mediaId}` and `GET /_synapse/admin/v1/fetch_event/{eventId}` (1.140.0, media metadata and event forensics), `use_admin` on the user redaction (1.135.0; an older Synapse ignores it and would send the redactions as the user, not as the admin the dialog confirmed), `type` on `GET /_synapse/admin/v1/rooms/{roomId}/state` (1.123.0), the user redaction and its status (1.116.0), suspension (1.110.0) and `GET /_synapse/admin/v3/users` (1.103.0, the user list and the dashboard). Everything else the app calls is served by Synapse 1.83.0 or earlier. The check covers only whether an endpoint or parameter exists, not behavior changes between releases. `after_ts` and `before_ts` on the user redaction (1.157) aren't sent (#600), so they don't raise the minimum.
- **Operations Tuwunel doesn't serve:** Tuwunel answers `404 M_UNRECOGNIZED` for the Synapse Admin API endpoints it doesn't serve ([status page](./tuwunel-admin-api-2026-11-24.md)). For the ones the app uses (media quarantine and protection, shadow-banning users, event reports, account validity, experimental features, background updates, room statistics by database size), the app refuses the operation with the "not supported by this homeserver" warning instead of sending it. Each page looks the same as on Synapse. Pages that load such data by themselves stay quiet: the dashboard leaves the latest reports and the largest rooms empty, and user details leave out the experimental features.
- **Remote media cache purge on Tuwunel:** Tuwunel selects cached remote media for `POST /_synapse/admin/v1/purge_media_cache` by when the file was stored (≈ downloaded), not by last access as Synapse documents, so it would also remove remote media that was used recently. The app refuses the purge on Tuwunel with the "not supported by this homeserver" warning, as it refuses bulk local media deletion (#542).
- **User list on Tuwunel:** Tuwunel ignores `order_by` on `/_synapse/admin/v3/users` and always sorts by user ID, and it stores no account creation time (it sends `creation_ts` `0`). On Tuwunel, sorting the user list by anything but user ID is refused with the "not supported by this homeserver" warning; the dashboard's latest users stay empty but its user count remains. A creation date of `0` or none is shown as "unknown" on every server.
- **Tuwunel read-only differences the app accepts:** Some read-only results differ from Synapse's and the gateway can't correct them cheaply, so the app shows them as Tuwunel returns them: the room list search matches a room ID only when it equals the search term in lower case and searches the whole alias instead of its localpart; the user list's name filter is case-sensitive; before Tuwunel 2.0.0 the user list can include accounts of other servers; and a history purge's status is lost when Tuwunel restarts (reported as "status unknown").
- **Bulk local media deletion on Tuwunel (#542):** Tuwunel (1.8.1 to 2.0.0) selects media for `POST /_synapse/admin/v1/media/delete` by the file's modification time (≈ upload) instead of last access, so it would delete recently used media that the confirmation promises to keep. It does honor `keep_profiles`: it keeps user and room avatars, as Synapse does. The app refuses the operation on Tuwunel with the "not supported by this homeserver" warning; the card itself looks the same as on Synapse.
- **Account actions on the signed-in admin (#584):** Synapse refuses only revoking one's own admin rights. Locking, suspending or shadow-banning one's own account, or deactivating it, would end or restrict the session the app runs on, so the user page disables these for the signed-in account. Resetting one's own password stays available: with "Log out all devices", Synapse logs out every other session of the user and keeps the one that sent the reset (`synapse/handlers/set_password.py` at v1.165.0). The comparison with the signed-in user ID is ordinal.
- **Own password reset on Tuwunel (#584):** Tuwunel (1.8.2 and 2.0.0) removes every device of the user when `logout_devices` is set, including the session that sent the reset, so resetting the signed-in admin's own password would sign the admin out of the app. The app refuses resetting the signed-in admin's own password on Tuwunel with the "not supported by this homeserver" warning, whatever the switch says. Resetting another user's password is unaffected, because the admin's session isn't one of that user's devices, and Tuwunel then does what Synapse does. Tuwunel's reset also reactivates a deactivated account (it marks deactivation by an empty password, and the reset writes a new one), while Synapse stores the password and leaves the account deactivated. The page doesn't offer a reset for a deactivated account, and the Tuwunel gateway reads the account before a reset and refuses it for a deactivated one, so that an account deactivated elsewhere in the meantime isn't reactivated.
- **Password changes the homeserver refuses (#584):** With Matrix Authentication Service enabled, Synapse doesn't serve `reset_password`; with `password_config.localdb_enabled: false`, it refuses a password on reactivation. Both show the operation's localized error. The app doesn't detect either configuration beforehand.
- **Partial account edits (#584):** `PUT /_synapse/admin/v2/users/{userId}` documents `admin` as defaulting to `false`, but Synapse and Tuwunel apply that default only when creating a user; for an existing account they change only the fields the body contains. Every edit therefore sends only the fields it changes, and the edit is sent only for an account the homeserver knows, so that it never creates one (the mirror of the create-only check).
- **Devices of the signed-in admin (#598):** Deleting the device whose access token the app uses would end the app's session, so the user page doesn't offer it, and the service refuses it with a warning if asked. The app learns its device ID from `/_matrix/client/v3/account/whoami`, which every login and session restore already calls. If the homeserver reports no device ID (for example for some appservice tokens), no device of the signed-in admin's own account can be deleted from the page; other users' devices are unaffected.
- **Devices that are already gone (#598):** Synapse and Tuwunel both answer a deletion of a device the user no longer has with success, so the result reports the deletion and the reloaded list no longer shows it. Renaming a device that is gone fails with the operation's localized error.
- **Devices and connections on Tuwunel (#598):** Tuwunel (1.8.2, 2.0.0) stores no user agent, so the device list and the recent connections show it as unknown. Its `whois` returns each device's last IP and time once, instead of Synapse's history of IP and user agent combinations, so Recent connections lists one entry per device there. It reports `dehydrated` only for a user who has a dehydrated device; a missing value is shown as not dehydrated. These are read differences the app accepts. Renaming (with the same 100-character limit) and deleting devices behave as on Synapse.
- **Deleting all of a user's media (#599):** `DELETE /_synapse/admin/v1/users/{userId}/media` deletes the uploads on one page of the user's media list and returns how many it deleted, without a `next_token`. Unlike the bulk local media deletion (#542), it spares neither protected nor quarantined media, nor media used as an avatar (Synapse v1.165.0 `UserMediaRestServlet`). The app always asks for the first page, because moving the offset would skip media as the list shrinks. A file Synapse can't remove from disk (other than one already missing) stays in the list and isn't counted, and Tuwunel leaves out a deletion that fails; a request that deletes nothing therefore doesn't mean nothing is left, which is why the app reads the list at the end. Tuwunel 1.8.2 and 2.0.0 serve the endpoint with the same parameters and result ("one page per call"). After 100 requests (10,000 uploads), the app stops and reports the number left; running it again continues.
- **Redacting a user's events (#600):** What Synapse v1.165.0 does (`RedactUser` in `rest/admin/users.py`, `handlers/admin.py`):
  - **Rooms:** an empty `rooms` list becomes the rooms the user is joined to plus the rooms they're banned from. Rooms the user has left aren't included. That covers every room of a deactivated account, because deactivation leaves them; the admin selects them instead.
  - **Events:** in each room, Synapse takes the user's newest `limit` events, by the time the server received them, of the types `m.room.message`, `m.room.encrypted` and `m.room.member`. It redacts those that aren't redacted yet, and of the membership events only joins. Reactions, stickers and other state events stay. A `limit` of `0` counts as the default 1000.
  - **Sender:** without `use_admin`, Synapse sends each redaction as the user. The Matrix authorization rules reject an event from a sender who isn't joined, so in a room the user has left the redactions fail unless "redact as admin" is on and the admin is joined there with the power level to redact.
  - **Failures:** an event that can't be redacted is recorded in `failed_redactions` and doesn't stop the task, which still ends as `complete`. Synapse doesn't report how many events it redacted, so the result names only the failures. While a redaction of the same user is active, Synapse refuses a new one, which shows the operation's usual error.
  - **Status:** it exists only by `redact_id`. Synapse's docs keep it for 24 hours after the task ends, or until Synapse restarts. The app keeps the ID in memory, so an app restart or another replica loses it, as for a history purge.
- **No time range for redactions (#600):** `after_ts` and `before_ts` exist since Synapse 1.157. An older Synapse ignores them and would redact events of any age, which is more than the admin confirmed. Per-operation version checks aren't planned (§14, #562), so the dialog offers no time range.
- **Redaction on Tuwunel (#600):** Tuwunel 1.8.2 and 2.0.0 serve both endpoints with Synapse's inputs and status names (1.8.1 serves neither). However, they take the `limit` window in reverse timeline order instead of by received time, and they redact through a different permission path. The same request can therefore redact other events than Synapse would. The app refuses the redaction and its status read on Tuwunel with the "not supported by this homeserver" warning and sends nothing. The dialog looks the same as on Synapse.
- **Making a room admin (#587):** What Synapse v1.165.0 does (`MakeRoomAdminRestServlet` in `rest/admin/rooms.py`):
  - **Who grants the power:** Synapse picks the local user with the highest power level in the room's `m.room.power_levels` (room creators count too in room versions where creators have unlimited power) who is still joined, and sends the new power levels as that user. Without a power levels event, it uses the room creator if the creator is local. If no such user is joined, or the user lacks the power to change power levels, the request fails (`400`, "No local admin user in room"). Making a room admin therefore can't recover a room after every local user with that power has left or been deactivated (deactivation leaves every room); it helps when such a user is still joined but unavailable.
  - **What is granted:** the target gets that user's power level (100 if it is a creator who isn't listed). Synapse doesn't check the target's server, so a user on another server can be made admin.
  - **Invite:** after the power level change, Synapse invites the target as that local user, unless the target is joined or invited already or the room's join rule is `public`. The answer (`{}`) doesn't say whether an invite was sent, so the result says it conditionally. The target still has to join; making the signed-in admin room admin doesn't join the admin to the room.
- **Joining a local user (#587):** Synapse v1.165.0 (`JoinRoomAliasServlet`) accepts only an existing local user, compares the server name exactly, and, unless the room's join rule is `public` (or the room has no join rule), first invites the user as the requesting admin, then joins the user. The admin must therefore be joined with the power to invite in every room that isn't public, restricted rooms included; the invite stays in the room's history even if the join then fails. Inviting a user who is already joined fails, which is why the dialog refuses a user the page lists as a joined member. Without servers to join through, a room this server has left can't be joined: Synapse then has no server to join through and answers `404`. The join dialogs therefore take servers, and the user page also an alias (#606, see "Joining by alias or through servers").
- **Room recovery on Tuwunel (#587):** Tuwunel 1.8.2 and 2.0.0 serve both endpoints, with differences:
  - **Make room admin:** checked for 1.8.2, 1.9.4, 2.0.0 and 2.1.0 (`make_room_admin` in `src/service/admin/grant.rs`, #607):
    - **Hangs on the invite before 2.1.0:** Tuwunel 1.8.2 through 2.0.0 hold the room's state lock while they send the invite, and the invite waits for the same lock. When the target needs an invite, the request never returns, and no event can be sent in that room on that server until it restarts. Tuwunel 2.1.0 takes the lock only after the invite.
    - **Directory instead of join rule:** Tuwunel skips the invite for a room that is listed in the public room directory or whose join rule is `public`; Synapse checks only the join rule. In a listed room that isn't publicly joinable (invite-only, knock or restricted), the target would get the power but no invite, and the gateway can't send the invite as the local user Synapse uses. 2.1.0 still does this.
    - **Order of writes:** Tuwunel invites the target before it changes the power levels, Synapse after. When the invite fails, Tuwunel has written nothing, while Synapse has already granted the power.
    - **Granting user:** Tuwunel picks it among all joined local users by their effective level, Synapse among the local users listed in the power levels (and the creators where creators have unlimited power). The granted level differs only if `users_default` is above every joined listed local user's level, if no joined local user is listed, or if the room has no power levels event. Among users tied for the highest level, the two servers may pick different senders for the same level.
    - The app refuses Make room admin on Tuwunel with the "not supported by this homeserver" warning and sends nothing; the dialog looks the same as on Synapse. Offering it where the result matches Synapse's needs a check for Tuwunel 2.1.0 or later (§14) or a 2.1.0 minimum, plus a refusal for listed rooms whose join rule isn't `public` (#607).
  - **Join user:** Tuwunel 1.8.2 never invites first, so the join fails in a room that isn't public. Tuwunel 2.0.0 invites first only when the user couldn't join otherwise, so it skips the invite for a restricted room whose allowed room the user is in, and doesn't require the admin to be in the room there. The Tuwunel gateway does what Synapse does before the join: it reads the room's join rule and, unless it is `public` or missing, invites the user as the signed-in admin through the Client-Server API. Tuwunel 2.0.0 then sees the invite and doesn't invite again. The result matches Synapse's, including the requirement that the admin is in the room with the power to invite.
- **Joining a user from the user page (#605):** Synapse v1.165.0 refuses to join a suspended account (`403`, `USER_ACCOUNT_SUSPENDED`), because the admin join isn't sent as the server; the page disables "Join to room" for it. Synapse doesn't check whether the account is deactivated and would join it, but nobody can use a deactivated account, so the page disables the action for it too. The Matrix authorization rules refuse an invite to a joined or banned user, and Synapse invites before it joins in every room that isn't public, so the dialog refuses rooms the user is joined to or banned from (the app has no unban). An invited or knocking user can be invited again, so those rooms are offered. The user's memberships list only rooms this server knows (Synapse's docs), and the picks come from that list; a typed room ID is sent as typed after the form check.
- **Joining by alias or through servers (#606):** What Synapse v1.165.0 does (`JoinRoomAliasServlet`, `ResolveRoomIdMixin`, `RoomMemberHandler`):
  - **`server_name`:** the reference doesn't document it, but the handler reads every `server_name` query parameter as the servers to join through. Tuwunel 1.8.2 and 2.0.0 read it the same way.
  - **Alias:** Synapse resolves it through the room directory (locally, or by asking the alias's server) and joins through the servers the directory returns, with the alias's server first. It replaces any `server_name` with them. Tuwunel does the same (`resolve_alias`). An unknown alias fails with `404`.
  - **Rooms this server isn't in:** when the last local user leaves a room, Synapse deletes the room's current state, so it finds no join rule, sends no invite, and joins remotely through the servers. The remote server then decides by the room's rules: a public room admits the user, while an invite-only room refuses the join unless the user is invited. Without servers, the join fails with `404`. Tuwunel 2.0.0 also skips its own invite when this server isn't in the room. Tuwunel keeps a room's state after leaving it, so the gateway checks for a joined local user before reading the join rule; otherwise it would invite where Synapse doesn't, and that invite would fail.

## 13. Risks

Technical and operational risks of the baseline (connect-time checks after login, `DP_PASSPHRASE`, `TRUSTED_PROXIES`, upstream API changes, the `LibMatrix` submodule, in-memory state, the font CDN) are tracked in [ARCHITECTURE.md §10](./ARCHITECTURE.md#10-technical-debt--risks). Use this table for product and feature risks, such as those of a `[Planned]` feature.

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Filtering a large room in the gallery checks many items, one admin API request each (#523). | Medium | Medium: load on the homeserver, a slow search | At most 5 batches of 20 lookups per load; more only after "Check more"; lookups already made are kept for the session's gallery and not repeated; unfiltered loading stays lazy. |
| Synapse marks its room deletion status API as experimental and subject to change (#518). | Low | Medium: no banner, or a missed result | A status value the app doesn't know counts as unknown and stops the checks with a message; a missing endpoint means no banner, not an error; the deletion request itself doesn't depend on the status API. |
| An account edit sends more fields than the admin changed, for example `admin: false`, and demotes or reactivates an account (#584). | Low | High: an admin loses rights, a deactivated account signs in again | A typed request that leaves unset fields out; wire tests pin the exact body of every edit; edits are sent only for an existing account. |
| An admin deletes a compromised account's devices but keeps its password, and the attacker signs in again (#598). | Medium | High: the account stays compromised | The delete confirmation says that deleting devices doesn't change the password; Reset password is on the same page. |
| An admin deletes all of a user's media expecting protected media or avatars to be kept, as the bulk deletion does (#599). | Medium | High: media other users rely on is gone, without undo | The confirmation names what is deleted, protected, quarantined and avatar media included, and that it can't be undone. |
| An admin redacts a deactivated spammer's events in "the user's rooms" and expects them gone, but the account has left every room, so nothing is redacted and the redaction still reports success (#600). | High | Medium: the spam stays visible | The dialog shows how many rooms "the user's rooms" covers, says when that is none, and offers every membership, rooms the user left included, under "Selected rooms"; it says that redactions there need "redact as admin". |
| An admin enters a reason that names the reporter or other private details, and every room member sees it in the redactions (#600). | Low | Medium: the reason can't be taken back | The reason field says that room members see it; it is optional. |
| An admin makes themselves room admin to rescue a room whose local admins have all left, and the request fails, or the admin expects to be in the room afterwards (#587). | Medium | Low: nothing changes, the admin has to find another way | The dialog says that a local user with the power to change power levels must still be joined, and that the user is invited, not joined; Join user is next to it. |
| An admin joins a user to an invite-only room without being in it, and the join fails (#587). | Medium | Low: nothing is joined, an error is shown | The dialog repeats the reference: the server administrator must be in the room and have permission to invite users. |
| A compatible homeserver deviates from Synapse in a way not yet known, so an operation runs with that server's semantics under Synapse's wording. | Medium | High for destructive operations: more is deleted or changed than the admin confirmed | Compare endpoints against the Synapse Admin API reference and the server's source, as for #540–#545; correct a known deviation in the server's gateway, or refuse the operation with `OperationNotSupportedByHomeserverException`. |

## 14. Open Questions

- **Minimum server versions per operation (deferred 2026-11-24; #562 closed as not planned for now):** Should a server's gateway check the server version before each operation (for example a higher Tuwunel minimum for some admin operations than the >= 1.8.2 the login probe requires) and throw `OperationNotSupportedByHomeserverException` below it? Open: whether Client-Server API methods are included or only admin API methods, how a version that can't be parsed counts (today `IsTuwunelAdminCapable` treats it as capable and lets the probe decide), and how a test covers the methods a server's gateway inherits without overriding them. First use cases: shadow login exists on Tuwunel only from 1.8.2 (#558), and making a room admin doesn't hang on the invite only from Tuwunel 2.1.0 (§10, #607).
