# AGENTS.md

## Project Overview

- **Purpose:** Self-hosted .NET 10 Blazor Server web app for administering Matrix Synapse (>= 1.145.0) and compatible homeservers (such as Tuwunel >= 1.8.2) via the Matrix Client-Server and Synapse Admin APIs, bundled with `LibMatrix` and `ArcaneLibs` git submodules and licensed under AGPL-3.0.
- **Primary users / consumers:** Matrix homeserver administrators only (not general Matrix end users).
- **Status:** Active Development (latest release `v1.16.1`) — auth, dashboard, user/room/media management, room recovery (make room admin, join a local user), room gallery, room history, event reports, event forensics, registration tokens, federation destinations, server notices, background updates, bulk media maintenance, localization (EN/DE/FR), Tuwunel >= 1.8.2 support, and MudBlazor themes are implemented (see [SPEC.md](./SPEC.md)).
- **Owner / team:** Benjamin Aicheler

## Setup & Commands

```bash
# Initialize submodules and restore NuGet dependencies
git submodule update --init --recursive
dotnet restore

# Start local development server (http://localhost:5235 / https://localhost:7256)
dotnet run --project src/SynapseAdmin/SynapseAdmin.csproj

# Build and run with Docker (local build vs pre-built GHCR image)
docker compose -f docker-compose.build.yml up --build
docker compose up -d

# Build & static type/nullability check (C# compiler)
dotnet build

# Run all unit, bUnit component, and integration tests
dotnet test

# Run a single test class or test method
dotnet test --filter "FullyQualifiedName~TestClassOrMethodName"
```

**Prerequisites:** .NET 10 SDK (or Docker + Docker Compose); initialized git submodules (`LibMatrix/`). For Docker bind mounts (`./logs`, `./keys`), directories must be writable by UID `1654` (`chown -R 1654:1654 logs keys`), and `DP_PASSPHRASE` should be set in production.

## Code Conventions

- **N-Tier Separation:** Presentation (`.razor` / `.razor.cs`) handles UI state, interaction, and ViewModel display only. Application Services (`Services/`) handle business logic, Matrix orchestration, and ViewModel mapping. Gateways (`Infrastructure/Gateways/`) handle all wire-level HTTP, URI encoding, and JSON concerns and return structured DTOs/nullable models—never raw `HttpResponseMessage` or protocol-leaking SDK objects.
- **ViewModel Mapping:** Services turn gateway DTOs into ViewModels with extension methods in `Extensions/Mapping/` (one `<Area>MappingExtensions` class per area, e.g. `ToViewModel` / `ToViewModels` / `ToDetailViewModel`), not with object initializers inside the service (#435–#437). The mapper only copies fields. The service keeps its `OperationResult` and null-result handling, and so does page assembly such as `UserMediaPageViewModel`'s offset and totals. Add a property-by-property test for each new mapper to `MappingExtensionsTests`, including the `null` → empty defaults.
- **Interfaces & DI:** Always extract an interface in `src/SynapseAdmin/Interfaces/` for every service. Register services in `Program.cs` and inject them into components using `[Inject]`. Components use `IMatrixAuthStateService` for the login state, never the concrete `MatrixAuthenticationStateProvider` (#451). `Program.cs` registers the interface as a second name for the scoped `AuthenticationStateProvider`, so both resolve to the same instance in a circuit (`AuthStateProvider_IsOneMatrixProviderPerCircuitScope`). Keep the `AuthenticationStateProvider` registration: Blazor resolves the base type.
- **Gateway Pattern & Capability Checks:** Services talk to Matrix only via `IMatrixGateway` (from `IMatrixSessionService`); unauthenticated login/discovery uses `IMatrixAuthGateway` (`HomeserverDiscoveryClient`), which acts as a factory for authenticated `IMatrixGateway` instances. Implement missing Synapse Admin endpoints in `SynapseAdminGateway` using `ClientHttpClient`—never modify `LibMatrix/`. Reuse the request helpers: `MatrixGatewayBase`'s protected `SendDeleteAsync` (see Always) and `SendDeleteAsync<TResponse>` for a DELETE whose JSON answer is read (an empty body returns `null`, #518), and `SynapseAdminGateway`'s private `GetWithCompatibilityOptionsAsync<T>` (see Known Pitfalls), `GetOptionalStatusAsync<T>` for a status read where `404`, `M_NOT_FOUND` or `M_UNRECOGNIZED` means "none" (#518), and `PostEmptyAsync(url, cancellationToken)` for a POST that sends `{}` and reads no response body (#442). Call `ClientHttpClient` yourself instead of a `LibMatrix` method that takes no `CancellationToken`, as `MatrixGatewayBase` does for the Client-Server alias and directory calls (#580). Encode path segments and query values with `.UrlEncode()` (form encoding), except a room alias in a path, which takes `Uri.EscapeDataString`: an alias may contain whitespace, form encoding sends a space as `+`, and a path keeps `+` as it is, so the request would name another alias (#580). A device ID in a path takes `Uri.EscapeDataString` for the same reason: clients choose device IDs, which may contain a space (#598). Encode opaque tokens such as `since` and `next_token` too: Synapse's public room `since` is standard base64 and can contain `+` (#580). Take each endpoint's HTTP method from the Synapse Admin API reference or the [Matrix Client-Server spec](https://spec.matrix.org/latest/client-server-api/), not from `LibMatrix`: it sends `PUT` for the quarantine endpoints, which Synapse registers as `POST` only (#516), and `POST` for setting room directory visibility, which the spec defines as `PUT` (#517). Take where each parameter goes (path, query string or JSON body) from the same reference: `LibMatrix` sends the shadow login's `valid_until_ms` as a query parameter, which Synapse ignores, so the token never expired (#539). In Razor components, check `IMatrixGateway.SupportsAdminApi` (never a concrete gateway type check such as `is SynapseAdminGateway`).
- **Synapse Admin API as the Contract:** The UI offers only operations Synapse supports and describes them as the [Synapse Admin API reference](./synapse-admin-api-2026-11-23.md) does, in the same words for every homeserver: no labels, hints or options per server. Services may call several endpoints and add logic, but never change for a server: nothing outside `Infrastructure/Gateways/` compares `ServerBrand` (the dashboard only displays it). A gateway corrects another server's deviation so that the result matches Synapse's (#541). Where it can't, it throws `OperationNotSupportedByHomeserverException` (a `NotSupportedException`) before sending anything, instead of running the operation with different semantics. A difference the gateway can't correct is accepted only if the operation the admin starts does what Synapse does. The difference may only be in how a read matches or what it lists, or in what the server does later on its own. Each accepted difference is recorded in SPEC.md §10. `RunGatewayCallAsync` reports it as the localized "not supported" warning (see Error Handling). Never throw a plain `NotSupportedException` for this: the service layer treats it as an ordinary failure. A server type with known deviations has its own gateway class derived from `SynapseAdminGateway` that overrides only the deviating methods (`TuwunelAdminGateway`, [ARCHITECTURE.md](./ARCHITECTURE.md) ADR 0006). `MatrixAuthGateway` picks the class after the probe, and no gateway method checks the brand. Make a private request helper `protected` when an override needs it. A request that only one server's override needs stays in that gateway class, such as `TuwunelAdminGateway`'s read of a registration token before an update (#548). Whether Tuwunel serves an endpoint at all is listed in its [status page](./tuwunel-admin-api-2026-11-24.md) for v2.0.0 and v1.8.1. The page doesn't describe parameters or behavior, so find deviations in Tuwunel's handler source, as for #541, #542 and #559. Don't add per-operation server version checks yet (SPEC.md §14).
- **Blazor & MudBlazor UI:** Use standard .NET 10 idiomatic C# and MudBlazor components (not raw Bootstrap) focused on data density. Always use code-behind (`.razor` + `.razor.cs`) with no inline `@code` blocks, and bind strictly to `Models/ViewModels/`—never pass raw SDK models to the UI.
- **Razor Markup Hygiene:** Comment `.razor` markup with Razor comments (`@* … *@`), never HTML comments (`<!-- … -->`). The component compiler strips HTML comments anyway, so they only mislead readers into thinking the text reaches the browser (#424). Don't repeat in a component what `Components/_Imports.razor` already provides to every `.razor` file under `Components/`: the `@inject IStringLocalizer<SharedResources> L` injection and its `@using` directives (e.g. `Microsoft.Extensions.Localization`, `SynapseAdmin.Resources`, `MudBlazor`) (#414, #429). `_Imports.razor` applies to markup only. `.razor.cs` code-behind can use the injected `L` property (same partial class), but needs its own `using` directives for any type it names. The component compiler drops the whitespace between an element and an `@if` block on the next line, so text inside the block renders glued to the element before it ("Blocked:No", #586). Show such values as components with their own spacing (chips, as the user and room status rows do), or keep the text on the element's line. An event handler renders on its own only after its first `await` and when it ends: state it sets later, before awaiting a long operation (a progress line, a Stop button), needs `StateHasChanged()` to show (`UserDetails.DeleteAllMedia`, #599).
- **Error Handling & Silent Cancellation:** Standardize all service methods to return `OperationResult` or `OperationResult<T>`. Run each gateway call through `sessionService.RunGatewayCallAsync(L, failureKey, logFailure, call)` (`GatewayCallExtensions`, #482–#488) instead of writing the ladder by hand. Without a session it returns `NotAuthenticated`. An `OperationCanceledException` becomes `OperationResult.Cancelled()` (`Severity.Normal`). A gateway's `OperationNotSupportedByHomeserverException` goes to `logFailure` and returns `L["OperationNotSupportedByHomeserver"]` with `Severity.Warning`, instead of the method's failure key. A read that a page runs by itself passes the optional `logRefusal`, which gets the refusal instead of `logFailure`, to log it at `Debug`. Any other exception, including a plain `NotSupportedException` (which streams, `System.Text.Json` and `LibMatrix` throw for unrelated reasons), goes to `logFailure` and returns `L[failureKey]`. It reads the session's gateway once and passes it to `call`. Put checks that must run after the session check at the start of `call`, and keep each method's null-result rule in `call`. `MatrixSessionService` keeps its own catches (login and session semantics). UI components report results through `SnackbarExtensions`, which skip `Severity.Normal` so navigation and reloads don't show error snackbars: `Snackbar.ShowResult(result)` shows every other result, `Snackbar.ShowFailure(result)` only failures. Both return whether they showed one. Don't compare `Severity` with `Severity.Normal` by hand. `Login` is the exception: it redirects or shows an inline alert instead of a snackbar. Never pass `ex.Message` or stack traces to `OperationResult.Failure`; log technical details server-side and return localized strings.
- **Null Gateway Results:** When a gateway call returns `null`, collection reads (lists, directories, aliases, memberships) return `OperationResult.Ok` with an empty collection. Single-resource reads (for example room/user details, returned as "not found") and operations return `OperationResult.Failure` (#395). The room deletion status is the exception (see Known Pitfalls).
- **Login Failures:** A failed password or token login never clears an existing session. `MatrixSessionService` replaces `Gateway` only after the new credentials are verified. Only `RestoreSessionAsync`, which replaces the session by design, clears `Gateway` on failure (#395).
- **Logging:** Inject `ILogger<T>` into services, log exceptions/errors for traceability, and sanitize untrusted strings with `.SanitizeForLogging()` (`LoggingExtensions`). Don't swallow an exception silently: a catch block that recovers logs what it caught, at `Debug` for expected failures (a denied clipboard write, a lost circuit) and at `Warning` for developer errors such as a theme that can't be created (O-01). Never log clipboard text, access tokens or raw event JSON. Serilog writes to stdout (`docker logs`) and rolling files in `logs/`.
- **Localization (`EN`, `DE`, `FR`):** Services localize **Business Outcomes** via `IStringLocalizer<SharedResources>`; `.razor.cs` injects `IStringLocalizer` only for **Interaction Logic** (dialog titles/messages, UI-only alerts, dynamic page titles), never service-level business text; `.razor` uses `IStringLocalizer` for **Static Layout** strings. See [LOCALIZATION.md](./LOCALIZATION.md).
- **Detail Pages & Destructive Actions:** Blazor reuses routed detail pages (`RoomDetails`, `UserDetails`, `RoomGallery`, and `EventForensics` for its `eventId` query, #521) when only the route parameter or query changes (e.g., `/rooms/A` → `/rooms/B`). On parameter change, clear the old model, cancel the previous `CancellationTokenSource`, and discard late responses before the first `await`. Capture the *currently displayed* entity ID before confirmation (never read the route parameter), include it in the confirmation prompt, and re-verify it is still displayed afterward; otherwise abort with `SelectionChangedActionAborted`.
- **Timezone & Themes:** Always convert/interpret user-facing timestamps via `ITimeZoneService` (initialized via JS interop in `MainLayout`), never `DateTime.Now` or `TimeZoneInfo.Local`. Add themes by implementing `IAppTheme` in `src/SynapseAdmin/Infrastructure/Themes/` (reflection-discovered, persisted in `ProtectedLocalStorage`; see [THEMING.md](./THEMING.md)).
- **Shared Helpers:** Reuse these instead of writing another copy (#460–#469, #482, #491): `GatewayCallExtensions.RunGatewayCallAsync` (see Error Handling), `MediaHelper.IsImage` / `IsVideo` / `IsAudio(mediaType, comparison)`, `MatrixIdHelper.IsOnServer(id, serverName)` (case-insensitive suffix, for links and lookups), `MatrixIdHelper.IsUserId(id)` / `IsLocalUserId(id, serverName)` (the full `@localpart:server` form; the server name compared exactly, as Synapse and Tuwunel compare it, for anything the homeserver will check as local, #587), `MatrixIdHelper.IsRoomId(id)` (both room ID forms, `!localpart:domain` and room version 12's domainless `!…`; no alias, #605), `MatrixIdHelper.IsRoomAlias(id)` (`#localpart:server`, split at the first `:`, spaces allowed inside the localpart, #606) and `IsServerName(name)` (the Matrix spec's server name: DNS name, IPv4 or bracketed IPv6, optional port, at most 255 characters; anchored with `\z`, because .NET's `$` also matches before a final line break), `SortDirection.ToSynapseDir(whenUnsorted:)`, `MatrixClaimTypes`, `GatewayConstants` (brand and version sentinels, the server-version path), `MediaPreviewLauncher` (preview URL and dialog), `DialogPresets.Small()` / `Medium()` / `SmallWithCloseButton()` / `MediumWithCloseButton()` (dialog options, a new instance per call), `StatusPoller<TStatus>` to follow a long-running homeserver operation (checks at once, then every `IntervalMs`, gives up after `MaxConsecutiveFailures` failed checks in a row, and applies an answer only while `IsCurrent` holds; `RoomDetails` uses it for history purge and room deletion, and `UserDetails` for a redaction of the user's events, each with its own constants and constant log templates, #535, #600), `SnackbarExtensions.ShowResult` / `ShowFailure` (see Error Handling), `JsRuntimeExtensions.TryCopyToClipboardAsync(text, Logger)` (returns `false` on any failure and logs it at `Debug` to the page's logger, never the text; each caller keeps its own messages), `RoomMediaItemViewModel.CopyMetadataFrom(other)` and `RoomMappingExtensions.ApplyMetadata(meta)` (room media metadata; `MediaId` is never copied), `FormatExtensions.FormatSize()` for every displayed byte size (media and database sizes), `UserDeviceService.IncludesOwnSessionDevice(gateway, userId, deviceIds)` before any operation that signs devices out (the device of the app's session comes from `IMatrixGateway.DeviceId`, the `/whoami` answer; if it is `null`, every device of the signed-in admin counts as it, #598). Each MIME check passes its `StringComparison` explicitly, because the media tables, the gallery and the preview sandbox deliberately differ. Pass `whenUnsorted: "f"` for rooms and users and `"b"` for event reports. Never change a `MatrixClaimTypes` value: issued authentication cookies contain them. Two places build the four session claims, in the same order: `MatrixAuthenticationStateProvider.CreateAuthenticatedState(gateway)` for the circuit (authentication type `"MatrixAuth"`, #438) and `AuthController.SignIn` for the cookie. Change both together. `RoomAliasesDialog` validates the alias server name ordinally and case-sensitively, so it doesn't use `MatrixIdHelper`.
- **bUnit Component Tests:** Tests in `tests/SynapseAdmin.Tests/Components/` extend `DetailPageTestBase` (MudBlazor + localization + recording `Stub` `DispatchProxy` doubles). Any class deriving from `BunitContext` must implement `IAsyncLifetime` (MudBlazor services are async-disposable only). Keep tests culture-independent (tests may run under `de_DE`): build expected strings via `IStringLocalizer<SharedResources>` and compare against `WebUtility.HtmlDecode(cut.Markup)` (Blazor leaves non-ASCII characters like `ä` unescaped). bUnit pitfalls: `WaitForAssertion` re-checks only after a render, so for work that doesn't re-render (background loops, failed polls) record state inside the stub or await a `TaskCompletionSource`. `TestSupport/BunitDefaults` raises bUnit's `DefaultWaitTimeout` from 1 s to 10 s for the whole test assembly, because the 1 s default made `WaitFor…` checks time out under full-suite load on slow hardware; don't pass a shorter timeout to a wait. `DetailPageTestBase.InvokeHandler` calls a handler without the render that follows a real click, so markup changed only by the handler may not update. Render before asserting on it (`cut.Render(p => p.Add(x => x.RoomId, id))`, with the same parameters, re-runs nothing on the detail pages), as `RoomDetailsBlockTests` does. `DisposeComponentsAsync()` swallows exceptions from a component's `DisposeAsync`; to see them, call `cut.InvokeAsync(async () => await cut.Instance.DisposeAsync())`. bUnit rejects `JSInterop.Setup<IJSObjectReference>("import", …)`, and its module references never fail on disposal; to simulate failing JS objects, register your own `IJSRuntime` (`JsDisposalTests`). The base class's `IDialogService` stub records `ShowAsync<TDialog>`'s arguments (title, parameters, options) but not the dialog type, so tell dialogs apart by their title (`UserDetailsPasswordTests`). A `MudForm` with a `Required` field keeps a submit button bound to its `IsValid` disabled until the input is validated, which shows only after the next render: wait for the button to be enabled before clicking it, or the click does nothing and an awaited `IDialogReference.Result` never completes (`ResetPasswordDialogTests`). A stub `IMudDialogInstance` renders no dialog content, so to test a dialog's form or buttons, register MudBlazor's real `DialogService` over the base class's stub, render a `MudDialogProvider` and open the dialog with `ShowAsync<TDialog>` (`DialogSnackbarTests`, `RoomAliasesDialogSnackbarTests`). A `MudTextField` with `Immediate="true"` handles only `oninput`, so enter text with `.Input(value)`; `.Change(value)` throws `MissingEventHandlerException`. A test that awaits a handler which opens a confirmation hangs the whole run, instead of failing, if a regression shows a confirmation that nothing answers: bound such an `await` with `.WaitAsync(TimeSpan.FromSeconds(10))` (`UserDevicesPanelTests`). A `MudRadio` handles only `onclick`, so choose it with `.Click()`; `.Change()` throws `MissingEventHandlerException`. `MudDialog` renders `TitleContent` outside the dialog component's own markup, so read a dialog's title from the rendered `MudDialogProvider` (`RedactUserEventsDialogTests`). A `MudNumericField` with `Min` raises a lower value to `Min` as it is typed, so a test of the minimum sees the corrected value, not a disabled button. A `MudListItem` renders its content in a `<p>`, which the HTML parser closes before a `<div>` such as a `MudChip`: find chips from `.Closest(".mud-list-item")`, not from the label's parent element (`LockedUserTests`). A `MudSelect` opens its items in a popover that bUnit doesn't render, so choose an item with `cut.InvokeAsync(() => select.Instance.ValueChanged.InvokeAsync(value))`, finding the select by its `Label` (`RoomListFilterTests`). `MudTable.NavigateTo(page)` loads the page itself when the table has `ServerData`, so don't call `ReloadServerData()` after it: that sends a second request (`Rooms.ReloadFromFirstPage`).
- **Tests Bound to Private Names:** Many tests reach private component members by name: `DetailPageTestBase.InvokeHandler(cut, "Name", …)` and `GetField<T>(instance, "name")`, and direct `GetMethod` / `GetProperty` / `GetField` calls, in more than 20 test files. Renaming or removing such a member still compiles, but those tests fail at run time. Before you rename or remove a private member of a component, search `tests/` for its name in quotes. If you move its logic elsewhere, keep the member as a thin wrapper. Keep the literal values tests pass as well, such as the gallery filter values `"all"`, `"local"`, `"remote"` and `"file"`. §0 of the [archived refactor plan](./docs/archive/2026-11-refactor-plan.md#0-snapshot) lists the names known when the refactor ended.
- **Test Doubles:** For an `IStringLocalizer<SharedResources>` outside bUnit, use `TestSupport/KeyLocalizer` (returns the key, ignores format arguments) or `FormattingKeyLocalizer` (applies `string.Format`) instead of a new nested class (#459). For logs, use `TestSupport/RecordingLogger<T>`, which records each call's level, template, named arguments and exception. Assert the template and the arguments, not the formatted text. `ResultAssert.Failure` / `Success` / `Cancelled` check a service result. `Stub.Fault(method, error)` makes a stubbed method return a task of its own return type faulted with `error`, as a failing async gateway call does. Each result-returning service has a table-driven `*ServiceCharacterizationTests.cs`; extend it when a method changes. In bUnit tests, `DetailPageTestBase.AssertPreviewShown` checks the media preview dialog call, `CancelDialogs()` closes every shown dialog as cancelled, `AssertDialogOptions(options…)` checks the options of every shown dialog in order, `Make<TResult>(kind)` builds a success without data, a failure or a silent cancellation (`"success"`, `"failure"`, `"cancelled"`), `WithData<T>(result, data)` copies a result's outcome into an `OperationResult<T>` for a stub method that returns data while the test shares one result between several actions, and `AssertSnackbars(results)` checks that exactly these results were shown, in order.
- **Formatting:** The repo-root `.editorconfig` is the formatting reference: LF, UTF-8, 4-space indent for C#/Razor/JS/CSS, 2-space indent for JSON/YAML/XML/project files, braces on their own line, trimmed trailing whitespace, final newline. It sets no analyzer severities, and CI doesn't check formatting. `LibMatrix/` keeps its own `.editorconfig` (`root = true`).
- **Tuning Values:** Timeouts, cache lifetimes, rate limits, cookie lifetimes and similar limits are named constants in the class that uses them, not configuration. Adding an environment variable or appsettings key for one is a feature and needs a SPEC.md entry first (#396).
- **Licensing:** All contributions must comply with AGPL-3.0.

## Workflow

We strictly follow **GitHub Flow** (direct commits to `main` are prohibited):

- **Before starting:** Sync `main` (`git checkout main && git pull origin main`). Read [SPEC.md](./SPEC.md), [ARCHITECTURE.md](./ARCHITECTURE.md), and if an active task is in progress, [PLAN.md](./PLAN.md) / [TODO.md](./TODO.md).
- **Feature Lifecycle (`SPEC → PLAN → TODO`):** [SPEC.md](./SPEC.md) is the living system specification—extend it for new features first (tag new additions `[Planned]` until implemented). For non-trivial changes, fill single-task [PLAN.md](./PLAN.md) (`Draft` → `Approved`), then populate [TODO.md](./TODO.md) and execute one task at a time (ignore `PLAN.md` / `TODO.md` unless `PLAN.md` is active in `Approved` or `In Progress`). When finished (before PR merge or when starting the next task), finalize `[Planned]` updates in [SPEC.md](./SPEC.md) (and [ARCHITECTURE.md](./ARCHITECTURE.md) if structure/flows changed) and clear/reset [PLAN.md](./PLAN.md) and [TODO.md](./TODO.md) back to their blank templates.
- **Where Documentation Goes:** AGENTS.md holds rules for working on the code (conventions, boundaries, pitfalls) and links elsewhere for background. [ARCHITECTURE.md](./ARCHITECTURE.md) describes how the system works and tracks technical and operational risks (§10). [SPEC.md](./SPEC.md) describes what the app does (requirements, acceptance criteria, edge cases written as behavior) and product or feature risks. Write each fact in one place and link to it from the others.
- **Behavior-Preserving Refactors:** For a change that must not alter behavior, follow [REFACTOR_RULES.md](./REFACTOR_RULES.md), whether or not it is a task in a refactor plan. ## Boundaries

### ✅ Always
- Extract an interface in `Interfaces/` for every new service and return `OperationResult` / `OperationResult<T>`.
- Propagate `CancellationToken` through services and gateways. For a raw HTTP `DELETE`, call `MatrixGatewayBase.SendDeleteAsync(url, content, cancellationToken)`, which instantiates `HttpRequestMessage(HttpMethod.Delete, url)` and calls `ClientHttpClient.SendAsync(reqMessage, cancellationToken)`, because `LibMatrix`'s `DeleteAsync`/`DeleteAsJsonAsync` lack token overloads (#440).
- Dispose `MediaDownload` (owns the `HttpResponseMessage`).
- Run `dotnet build` and `dotnet test` before pushing commits, unless they change only Markdown files.

### ⚠️ Ask first
- Before creating a new GitHub issue when none was provided, or before implementing High/Medium fixes after generating a code review report.
- Before adding NuGet dependencies, modifying `.github/workflows/`, changing Docker security settings, or updating the `LibMatrix/` submodule.

### 🚫 Never
- Commit or push directly to `main`, or run `git push --force` on shared branches.
- Commit secrets, credentials, access tokens, `DP_PASSPHRASE` production values, or real user PII.
- Modify the `LibMatrix/` submodule to work around Synapse Admin API gaps or quirks.
- Put bridge keys or tokens in URLs/query strings, or reintroduce a GET sign-in endpoint.
- Expose raw `ex.Message`, stack traces, or `HomeserverNotAllowedException` text to the UI.
- Read `IHttpContextAccessor` directly for client IP inside Blazor circuit handlers, or use per-circuit random rate-limit keys.
- Use `LibMatrix`'s `HomeserverResolverService`/`HomeserverProviderService` or `hsProvider.GetAuthenticatedWithToken`/`Login`/`GetRemoteHomeserver` on the auth path, or `GetMediaStreamAsync`/`GetMediaUrlAsync` for media downloads (no token/range; triggers an extra undisposed probe `GET` per request).
- Synthesize HTTP `206` locally from a non-seekable stream, or reintroduce `max-age` on protected media.
- Use `DateTime.Now`/`TimeZoneInfo.Local`, inline `@code` blocks, concrete gateway type checks in UI, or hard-coded English strings in bUnit tests.

## Security & Data Protection

[ARCHITECTURE.md](./ARCHITECTURE.md) describes how these mechanisms work: the login, cookie bridge and media flows in §5, data at rest in §4, configuration in §7, the destination policy and client IP handling in §8, and known limitations in §10. When you change them, keep these rules:

- **Cookie Bridge:** Start the handoff only through `IAuthCookieService` (`Login` and `NavMenu` use it). Bridge keys stay single-use, expire after 60 seconds, stay bound to the circuit's antiforgery token and travel only in the `POST /Auth/SignIn` body. Claim a key atomically (`Interlocked`), and reject a mismatched binding **without burning the key**.
- **Data Protection at Rest:** The key ring in `./keys` is encrypted with `DP_PASSPHRASE`. Renaming or moving `AesXmlDecryptor` makes the existing keys unreadable (see Dynamically Wired Code).
- **Rate Limiting & Client IP:** Throttle password logins per IP *and* per cross-IP `(homeserver, account)`, and token logins **per IP only** (#368). Never reintroduce a homeserver-only bucket. Keep the separate `"auth"` rate limiter on `POST /Auth/SignIn`. Get the client IP only through `IClientIdentityProvider`; a missing IP goes to the shared `"unknown"` bucket with a warning.
- **SSRF / Cleartext Policy:** Send every unauthenticated discovery and login request through `HomeserverDiscoveryClient`, so that `IHomeserverDestinationPolicy` checks the entry host, every `.well-known` hop, every redirect and the resolved socket IP. A non-empty `HOMESERVER_ALLOWLIST` stays a hard gate that fails closed. Show `HomeserverNotAllowedException` only as the localized `HomeserverNotAllowed` message. Calls after login are not re-checked at connect time (ARCHITECTURE.md §10), so don't rely on the policy there.
- **Media Streaming (`MediaController`):** `Download`, `Preview` and `Avatar` authorize, restore the session and open the media (`IMatrixGateway.OpenMediaAsync`, `ResponseHeadersRead`) **before** they evaluate `If-None-Match`, including `*` and `Range` requests (#370). Missing or quarantined media returns `404`, never `304`, and a `304` disposes the unread stream. Forward only a single `bytes` range, and only if an `If-Range` validator, when present, matches strongly (#372). Relay the homeserver's `206` (through `PartialMediaResult`), its `416`, or its full `200`. Fall back to `/_matrix/media/v3/download` only on `M_UNRECOGNIZED` or a bare `404`/`405`, never on `M_NOT_FOUND`. Keep `Cache-Control: private, no-cache` on protected media, so deletion, quarantine or revocation takes effect at once. `Download` and `Preview` set `X-Content-Type-Options: nosniff` themselves, in addition to the global middleware. This is deliberate defense in depth for user-uploaded content (#396), so don't remove it as a duplicate.

## Known Pitfalls

- **`GetFromJsonAsync` Option Mutation:** `LibMatrix`'s `MatrixHttpClient` mutates `JsonSerializerOptions` passed to `GetFromJsonAsync`. On endpoints with inconsistent types (e.g., numeric vs string `next_token`), always call `GetWithCompatibilityOptionsAsync<T>(url, cancellationToken)` in `SynapseAdminGateway`, which does `ClientHttpClient.GetAsync` + `JsonSerializer.DeserializeAsync(..., SynapseCompatibilityJsonOptions)` (`protected static readonly` field, using `JsonStringConverter`) (#439). Keep every `JsonSerializerOptions` in a `static readonly` field, as `SynapseCompatibilityJsonOptions` and `EventForensicsService.IndentedJson` do. A new instance per call rebuilds the serializer's metadata cache each time (CA1869, #430).
- **`MatrixHttpClient` Omits Null Properties:** `ClientHttpClient.PostAsJsonAsync`/`PutAsJsonAsync` always set `DefaultIgnoreCondition = WhenWritingNull`, overwriting the options a caller passes. Where Synapse treats an explicit `null` differently from an omitted field, mark the property `[JsonIgnore(Condition = JsonIgnoreCondition.Never)]` and assert the exact body in a wire-level test (`SynapseAdminRegistrationTokenUpdateRequest`, #519). A body serialized with `JsonSerializer.Serialize` for `SendDeleteAsync` does the opposite and writes every `null`: mark each optional field `[JsonIgnore(Condition = JsonIgnoreCondition.WhenWritingNull)]` (`SynapseAdminRoomDeleteRequest`, #543).
- **`MatrixHttpClient` Error Responses:** `ClientHttpClient.GetAsync`/`SendAsync` throw on a non-success response before the caller's own `EnsureSuccessStatusCode` runs: `MatrixException` for a Matrix JSON error body (`M_LIMIT_EXCEEDED` is retried after a delay), `HttpRequestException` for any other body. A `502` with a non-JSON body is retried, then fails with `InvalidDataException`. Only `SendUnhandledAsync` returns the raw response (`OpenMediaAsync`). Keep the gateways' `EnsureSuccessStatusCode` calls as a defensive fallback, and expect both exception types in gateway tests (`SynapseAdminGatewayCharacterizationTests`, #439).
- **Synapse Field & Timestamp Quirks:** Room Admin API uses `avatar` while User Admin/CS APIs use `avatar_url`. On `/_synapse/admin/v3/users`, `creation_ts` is in **milliseconds** (`FromUnixTimeMilliseconds` in `UserMappingExtensions.ToViewModel`); on `/_synapse/admin/v2/users/{userId}`, it is in **seconds** (`FromUnixTimeSeconds` in `UserMappingExtensions.ToDetailViewModel`). **Do not unify or alter these two conversions.**
- **Room Size Semantics:** `/_synapse/admin/v1/rooms` `order_by=size` sorts by `joined_members` (member count), not DB bytes. Synapse sorts `joined_members`, `joined_local_members`, `version`, `state_events` and `size` largest first with `dir=f`, so `RoomService` sends `dir=b` for an ascending sort on them; Tuwunel sorts every key ascending, so `TuwunelAdminGateway` reverses `dir` again for these keys (#541). Both use `RoomSortKeys`. Sort only by documented `order_by` keys: Synapse rejects others such as `room_type` with `400` (#540), and `alphabetical` is a deprecated alias of `name` (#545). DB byte size (`estimated_size`) comes from `/_synapse/admin/v1/statistics/database/rooms` without room names, so `RoomService` caches resolved names in `IMemoryCache`.
- **Room Gallery Filters Need Metadata (#523):** `/_synapse/admin/v1/room/{roomId}/media` returns bare `mxc://` URIs, so `RoomGalleryGrid`'s type filters and file-name search need a metadata lookup per item (one admin request each, no bulk endpoint). The grid classifies the source's items in order and looks up unknown ones in batches (`PageSize`, at most `MaxLookupBatchesPerLoad` per load). Don't filter on `MediaType` or `UploadName` without checking `_loadedMetadataMxcs`. A `[JSInvokable]` method such as `OnSentinelIntersected` renders nothing by itself: call `StateHasChanged()` after the last state change, and `IntersectionObserver` fires only when the sentinel *enters* the view, so a load that leaves it visible needs another trigger ("Check more").
- **Per-Homeserver Cache Keys:** `IMemoryCache` is shared by every session in the process, and sessions can be on different homeservers. A cache key for homeserver data must include the homeserver. `RoomService` builds its keys as `<prefix>:{HomeserverCacheScope}:{id}` (`room_name:…`, `active_purge:…`), where `HomeserverCacheScope` is the homeserver URL without a trailing slash, in lower case (#431). Use it for new `RoomService` caches, and scope caches in other services the same way.
- **Room Deletion Status (#518):** `DELETE /_synapse/admin/v2/rooms/{roomId}` only starts the deletion and returns a `delete_id`. `RoomDetails` finds a running deletion by room ID (`/_synapse/admin/v2/rooms/{roomId}/delete_status`) when it loads, and checks it by `delete_id` (`/_synapse/admin/v2/rooms/delete_status/{deleteId}`), so nothing is cached. A history purge status exists only by `purge_id`, which is why purges are tracked in `IMemoryCache`. Synapse's API docs say it keeps a deletion status for 24 hours after the deletion ends, or until it restarts (v1.165.0's task scheduler keeps finished tasks for 7 days), and mark the API as experimental. The gateway returns `null` for `404`, `M_NOT_FOUND` and `M_UNRECOGNIZED`, and `GetRoomDeletionStatusAsync` turns that `null` into `RoomDeletionState.Unknown` instead of a failure, so the page doesn't count it toward its cap of failed checks. Never show a deletion's or a purge's `error` text in the UI: `RoomService` logs it and the page shows a localized message. While either runs, `RoomDetails.IsRoomOperationRunning` disables the room actions. Tuwunel serves the same routes and status names but purges after failed evictions and doesn't report some failed purge steps, so `TuwunelAdminGateway` refuses the deletion and both status reads (#559). `GetActiveRoomDeletionAsync` runs on every room open and logs that refusal at `Debug`, not `Error`.
- **Bulk Local Media Deletion (#542):** `POST /_synapse/admin/v1/media/delete` deletes local media last accessed before `before_ts` (media never accessed counts from its upload, because Synapse doesn't set `last_access_ts` at upload) and larger than `size_gt`. Both conditions apply together. `keep_profiles` keeps media used as a profile, user directory or room avatar, and Synapse never deletes protected or quarantined media here. `total` is the number of deleted media IDs. Tuwunel (1.8.1 to 2.0.0) selects by the file's modification time (≈ upload) instead, so `TuwunelAdminGateway` refuses the operation (ADR 0006). It does honor `keep_profiles`.
- **Tuwunel Deletes Invalid Registration Tokens (#548):** Tuwunel (1.8.1 to 2.0.0) removes a registration token as soon as it is invalid (its uses reached `uses_allowed`, or `expiry_time` passed), the next time tokens are listed or checked. Synapse keeps such a token, and `uses_allowed: 0` is its documented way to invalidate one without deleting it. `TuwunelAdminGateway` therefore refuses a create or update that would leave the token invalid at once: a cap of `0`, a cap at or below the token's `completed` count (the update reads the token first), or an expiry in the past. Keep the dialog and `RegistrationTokenService` the same for every server.
- **Creating a User Modifies an Existing One:** `PUT /_synapse/admin/v2/users/{userId}` creates the user or, if the ID exists, modifies that account (Synapse answers `200` instead of `201`). `UserService.CreateUserAsync` therefore reads the user first and sends the `PUT` only when `GetUserDetailsAsync` returns `null`, which the gateway returns for `M_NOT_FOUND` only. `M_UNRECOGNIZED`, a bare `404` and every other error still throw, so they never count as "no such user". Keep this check in front of any new caller that means to create. The account edits need the opposite check: `UserService.EditExistingUserAsync` reads the user first and sends the `PUT` only when it exists, with only the edited field (#584). The `PUT` leaves an omitted field unchanged, `admin` included, although the reference documents `admin` as defaulting to `false`: that default applies only when creating. Never send `admin` from an edit that doesn't change it.
- **`from` Offsets vs `next_token` (#551):** Synapse documents `from` as the opaque `next_token` of the previous page. The numbered tables (users, event reports, user media) still send `from = page × pageSize`, so the pager can jump to any page: Synapse and Tuwunel implement `from` as an item offset (`ListPageOffsetTests`). A list read whole follows `next_token` instead: `FederationService.GetAllDestinationsAsync` leaves `from` out on the first request, passes each token back unchanged, stops only when the token is missing (never on `total`), fails the whole load when a page fails or a token repeats, and `FederationDestinations` keeps only a complete load.
- **Deleting All User Media (#599):** `DELETE /_synapse/admin/v1/users/{userId}/media` deletes one page of the user's uploads, protected and quarantined media and avatars included (unlike the bulk deletion, #542), and `total` is the number that call deleted. Always send `from=0`: the remaining media are reordered after each call. A call that deletes nothing doesn't mean the list is empty (Synapse keeps files it can't remove, Tuwunel leaves failed deletions out), so `UserService.DeleteAllMediaAsync` reads the list at the end. Once something is deleted, a cancellation or failure is a result that names the count, not the usual silent cancellation or failure key.
- **Redacting a User's Events (#600):** `POST /_synapse/admin/v1/user/{userId}/redact` only starts a background task and returns a `redact_id`; its status exists only by that ID, so `UserRedactionService` keeps it in `IMemoryCache` per homeserver and user (`active_redaction:…`, 24 h) with a compare-and-clear under a static lock (#522). Always send `rooms`: an empty list means the rooms the user is joined to or banned from (not left rooms, so not a deactivated account's rooms), so "Selected rooms" with none selected is refused and never sent as `[]`. A `limit` of `0` counts as 1000, so the service refuses a limit below 1. Never send `after_ts` / `before_ts` (Synapse before 1.157 ignores them, SPEC.md §10), and never log the reason (room members see it, and it may name people). A status `404` is `UserRedactionState.Unknown`, not a failed check. `failed_redactions` and `error` go only to the log (the first 20 failures, sanitized); the page shows the count.
- **User Media Pagination (#371):** `/_synapse/admin/v1/users/{userId}/media` `from` is an item offset (`next_token` = `from` + returned count, max `limit` default 100); page server-side with `from = page × pageSize` (`created_ts`/`b`). Totals across all uploads come from `/_synapse/admin/v1/statistics/users/media` searched by **localpart** (Synapse filters `user_id LIKE '@%' || term || '%:%'`, so full Matrix IDs never match and exact `user_id` must be picked from results); label page stats separately from totals.
- **Room Media Duplicates (#384):** `/_synapse/admin/v1/room/{roomId}/media` emits one entry per event reference (same MXC URI can appear in `local` or `remote`). `RoomService` keeps first occurrence and `RoomGalleryGrid` deduplicates defensively. Compare whole MXC URIs ordinally (never bare media ID or case-insensitively), and never key a dictionary on raw MXC URIs from this endpoint without deduplicating first.
- **Room Recovery (#587, #605, #606):** `POST /_synapse/admin/v1/rooms/{roomId}/make_room_admin` grants the target the power level of the highest local user in the room's power levels who is still joined, and sends the change as that user. Without such a user, or if that user can't change power levels, Synapse answers `400`, so it can't rescue a room whose local admins have all left. It answers `{}`, invites the target unless they are joined or invited or the join rule is `public`, and never joins them. Send `{}` for the signed-in admin (`SynapseAdminMakeRoomAdminRequest` with a `null` `user_id`, which `PostAsJsonAsync` drops), and don't check the target's server: Synapse doesn't. `POST /_synapse/admin/v1/join/{roomId}` accepts only local users, with the server name compared exactly (`MatrixIdHelper.IsLocalUserId`, not `IsOnServer`), and first invites the user as the requesting admin unless the join rule is `public` (no join rules event: no invite). Inviting a joined member fails, so `RoomUserActionDialog` refuses the joined members the page lists. Make room admin takes room IDs only. The join takes a room ID or an alias (#606): a room ID in the path is form-encoded as before, an alias takes `Uri.EscapeDataString` (#580). The servers to join through go in one `server_name` query parameter each. The reference doesn't document it, but Synapse's and Tuwunel's handlers read it; without servers, a room this server has left can't be joined (`404`). For an alias, both servers join through the servers its resolution returns and ignore `server_name`, so `RoomService` refuses servers given with an alias, and `UserJoinRoomDialog` disables its servers field for one. The success message names the answer's `room_id`, the room an alias reached. The dialog names the room and is the confirmation; `RoomDetails` re-checks the shown room afterwards. On Tuwunel, make room admin is refused, and `TuwunelAdminGateway.JoinUserToRoomAsync` corrects the join: Tuwunel 1.8.2 never invites first and 2.0.0 only when the user couldn't join otherwise, so the gateway reads the join rule and sends Synapse's invite through `POST /_matrix/client/v3/rooms/{roomId}/invite` before the admin join. Before that, it resolves an alias through the Client-Server directory and reads the room details: for a room without a joined local user (`joined_local_members` `0`) or one it doesn't know (`404`), it sends no invite. Synapse deletes a room's current state when the last local user leaves, so it finds no join rule there and invites nobody, while Tuwunel keeps the state, and its invite would fail. The join itself carries the alias or room ID and the servers as given. The user page joins the shown user through the same `IRoomService.JoinUserToRoomAsync` (#605): its `UserJoinRoomDialog` takes a typed room ID or a pick from the user's `leave`, `invite` and `knock` memberships and refuses `join` and `ban` (an invite to a joined or banned user fails), and "Join to room" is disabled for suspended accounts (Synapse refuses them with `USER_ACCOUNT_SUSPENDED`) and deactivated ones. Because the room is typed there, the service checks the room first (`IsRoomId` or `IsRoomAlias`), then the servers (`IsServerName`, after trimming and dropping blanks and duplicates), then the user. Both dialogs split their servers field with `Components/Shared/JoinServerInput` and return a `RoomJoinRequestViewModel`; Make room admin still returns the user ID as a `string`.
- **What Tuwunel Refuses:** Checked against Tuwunel's [status page](./tuwunel-admin-api-2026-11-24.md) and its handlers at v1.8.2 and v2.0.0 (SPEC.md §10). `TuwunelAdminGateway` refuses the operations Tuwunel doesn't serve (media quarantine and protection, room and user quarantine, event reports, account validity, experimental features, background updates, `statistics/database/rooms`), the remote media cache purge (it selects by storage time, not last access), the bulk local media deletion (#542), the room deletion and its status reads (#559), making a room admin (Tuwunel invites before it grants the power and skips the invite for an invite-only room listed in the public directory, #587; up to 2.0.0 it also never answers when it invites, and the room takes no more events until a restart, #607), redacting a user's events and its status read (Tuwunel takes the `limit` window in timeline order and redacts through another permission path, #600), registration tokens that would be invalid at once (#548), shadow-banning and lifting a shadow-ban (Tuwunel has none, #584), resetting the signed-in admin's own password (Tuwunel also removes the requester's device when it logs devices out) and resetting a deactivated account's password (Tuwunel's reset reactivates it; `ResetPasswordAsync` reads the account first, #584), and a user list sorted by anything but `name` (Tuwunel ignores `order_by`). It sets a `creation_ts` of `0` to `null` (Tuwunel stores none), and the pages show it as "unknown". Before you lift a refusal, check the endpoint on the status page and in the handler of the Tuwunel release that serves it. A read that a page runs by itself passes `logRefusal` to `RunGatewayCallAsync` and logs the refusal at `Debug` (dashboard, user details, event reports, background updates, the user list, the room deletion lookup); refused actions log their error. The dashboard reads the user count with its own `name` request, so that a refused latest-users read doesn't take the count with it.
- **Tuwunel & Generic Fallback:** Compatible servers (Tuwunel >= 1.8.2) return `AuthenticatedHomeserverGeneric`, so `MatrixAuthGateway` probes federation version + `/_synapse/admin/v1/server_version` and wraps them in `TuwunelAdminGateway` when the federation reports the Tuwunel brand (in any casing), or else in `SynapseAdminGateway`, which Synapse servers and servers of unknown brand use. Today's `SynapseAdminGateway` (formerly `SynapseCompatibleAdminGateway`) is not the SDK-based `[Obsolete]` class of that name removed in #397. A failed probe is soft (no admin API, or the default brand and version), but every probe catch is `catch (Exception) when (!cancellationToken.IsCancellationRequested)`: a cancelled probe must propagate, or a gateway without the admin API would be cached for the session (#391, #443, #444). `IsTuwunelAdminCapable` accepts Tuwunel >= 1.8.2 (1.8.1 doesn't serve seven endpoints the app calls), drops a suffix after the first `-`, and treats a version it can't parse as capable, so the active `server_version` probe decides. `IsSynapseAdminCapable` accepts Synapse >= 1.145.0, the oldest release that serves every admin endpoint and parameter the app sends (SPEC.md §10, "Synapse versions", #612). It reads only the release number at the start (`1.145.0rc1` and `1.165.0 (b=…)` qualify) and treats a version without one as capable. It checks the federation version and, when discovery already identified Synapse, the `server_version` answer; a server without a resolved brand isn't checked, because its version may follow another server's numbering. A new endpoint or parameter that an older Synapse lacks raises this minimum: find the first release that serves it in Synapse's source (its release tags), not only in the reference's "Added in" notes, which most endpoints lack.
- **Serilog Configuration Names:** Every enricher and sink named in `appsettings.json` (`Serilog:Enrich`, `Serilog:WriteTo`) needs its package referenced. Serilog skips a name it can't resolve and reports it only to its `SelfLog`, which the app doesn't enable, so the app starts without it and nothing says so (#498). `LoggingConfigurationTests` loads the shipped `appsettings.json` and fails on any such report. A test that enables Serilog's process-wide `SelfLog` joins `[Collection(SerilogSelfLogCollection.Name)]`, which runs alone.
- **Dynamically Wired Code:** These have no static caller in `src/` but are used at run time, so never delete, rename or move them as dead code (REFACTOR_RULES.md §3). `AesXmlDecryptor`: Data Protection writes its type name into every key file in `./keys`, so renaming it or changing its namespace makes the existing keys unreadable and invalidates every cookie and stored session. `[JSInvokable] RoomGalleryGrid.OnSentinelIntersected` (called from `gallery-interop.js`), and the JS modules imported by path string (`./js/auth-bridge.js`, `./js/gallery-interop.js`, `./js/timezone-interop.js`). Controller actions (routed by `[controller]/[action]`; JS and `NavigationManager` use their URLs), `PartialMediaResult.ExecuteResultAsync` (MVC result pipeline), `IAppTheme` implementations (reflection), `ClientIdentityCircuitHandler` (DI), the request/response DTOs in `Models/` and the private DTOs in `HomeserverDiscoveryClient` (`System.Text.Json`), and `public partial class Program` (`WebApplicationFactory<Program>`). `internal` members that only tests call (through `InternalsVisibleTo`), such as `UserService.MediaStatisticsSearchTerm`, `SynapseAdminGateway.Build*Url` and `LoginRateLimiter.IsAllowed`, are test hooks.
